# 스펙: 미니 방명록

Status: ready-for-agent

## Problem Statement

방문자가 회원가입이나 로그인 같은 번거로운 절차 없이 짧은 인사말을 남기고, 다른 사람들이 남긴 글을 한눈에 보고 싶어 한다. 동시에 글쓴이는 자신이 남긴 글을 나중에 고치거나 지울 수 있어야 하지만, 다른 사람이 내 글을 마음대로 고치거나 지워서는 안 된다. 계정이 없는 상황에서 "이 글의 주인인지"를 확인할 방법이 필요하다.

## Solution

이름, 메시지, 작성 시각이 함께 쌓이는 한 페이지짜리 방명록을 만든다. 누구나 이름·메시지·글 비밀번호를 입력해 글을 남길 수 있고, 전체 글은 최신순으로 한 번에 보인다. 글쓴이는 글을 남길 때 정한 글 비밀번호를 다시 입력해 그 글의 메시지를 수정하거나 글을 삭제할 수 있다. 비밀번호가 틀리면 요청은 거부되고 그 자리에서 안내 문구가 표시된다. 페이지 상단에는 개발자 이름과 학번(`개발자: 이동규 (202404265)`)이 표시된다.

## User Stories

### 조회

1. 방문자로서, 페이지에 들어가자마자 전체 글 목록을 보고 싶다. 그래야 다른 사람들이 남긴 말을 읽을 수 있다.
2. 방문자로서, 목록이 최신 작성 시각 순으로 정렬되어 있기를 원한다. 그래야 가장 최근 글을 먼저 볼 수 있다.
3. 방문자로서, 각 글의 이름, 메시지, 작성 시각을 함께 보고 싶다. 그래야 누가 언제 무슨 말을 남겼는지 알 수 있다.
4. 방문자로서, 작성 시각이 한국 시간 기준 `YYYY-MM-DD HH:mm` 형식으로 보이기를 원한다. 그래야 헷갈리지 않고 시각을 읽을 수 있다.
5. 방문자로서, 메시지에 들어간 줄바꿈이 그대로 보이기를 원한다. 그래야 글쓴이가 의도한 모양대로 읽을 수 있다.
6. 방문자로서, 수정된 글에는 "(수정됨 · 수정 시각)" 표시가 보이기를 원한다. 그래야 작성 시각 이후에 내용이 바뀌었다는 걸 알 수 있다.
7. 방문자로서, 글이 수정되어도 목록에서의 위치가 바뀌지 않기를 원한다. 그래야 순서가 작성 시각 기준으로 일관된다.
8. 방문자로서, 글이 하나도 없을 때 "아직 글이 없습니다" 같은 안내를 보고 싶다. 그래야 페이지가 고장 난 것이 아님을 알 수 있다.
9. 방문자로서, 어떤 경우에도 다른 사람의 글 비밀번호(또는 그 흔적)를 볼 수 없기를 원한다. 그래야 내 비밀번호도 안전하다고 믿을 수 있다.
10. 방문자로서, 페이지 상단에서 개발자 이름과 학번을 보고 싶다. 그래야 누가 만든 방명록인지 알 수 있다.
11. 방문자로서, 메시지에 HTML이나 스크립트처럼 보이는 문자열이 있어도 그냥 글자로 보이기를 원한다. 그래야 악의적인 글이 페이지를 망가뜨리지 못한다.

### 작성

12. 방문자로서, 로그인 없이 이름, 메시지, 글 비밀번호만 입력해 글을 남기고 싶다. 그래야 부담 없이 인사를 남길 수 있다.
13. 글쓴이로서, 글을 남기면 목록 맨 위에 내 글이 바로 보이기를 원한다. 그래야 제대로 등록되었음을 확인할 수 있다.
14. 글쓴이로서, 글을 남긴 뒤 작성 폼이 비워지기를 원한다. 그래야 실수로 같은 글을 두 번 올리지 않는다.
15. 글쓴이로서, 이름을 비우거나 공백만 입력하면 거부되고 이유가 표시되기를 원한다. 그래야 무엇을 고쳐야 하는지 안다.
16. 글쓴이로서, 이름이 20자를 넘으면 거부되고 이유가 표시되기를 원한다.
17. 글쓴이로서, 메시지를 비우거나 공백만 입력하면 거부되고 이유가 표시되기를 원한다.
18. 글쓴이로서, 메시지가 500자를 넘으면 거부되고 이유가 표시되기를 원한다.
19. 글쓴이로서, 글 비밀번호가 4자 미만이거나 64자를 넘으면 거부되고 이유가 표시되기를 원한다.
20. 글쓴이로서, 이름과 메시지의 앞뒤 공백은 자동으로 정리되기를 원한다. 그래야 불필요한 공백이 저장되지 않는다.
21. 글쓴이로서, 입력값 오류로 거부되더라도 내가 입력한 내용이 지워지지 않기를 원한다. 그래야 다시 다 입력하지 않아도 된다.
22. 글쓴이로서, 브라우저에서도 길이 제한이 미리 걸려 있기를 원한다. 그래야 제출하기 전에 문제를 알 수 있다.
23. 글쓴이로서, 제출 중에는 버튼이 비활성화되기를 원한다. 그래야 중복 제출을 막을 수 있다.
24. 글쓴이로서, 비밀번호 입력칸의 글자가 가려지기를 원한다. 그래야 옆 사람이 볼 수 없다.

### 수정

25. 글쓴이로서, 내 글의 "수정" 버튼을 누르면 그 글 안에 메시지 편집칸과 글 비밀번호 입력칸이 펼쳐지기를 원한다. 그래야 다른 화면으로 이동하지 않고 고칠 수 있다.
26. 글쓴이로서, 편집칸에 기존 메시지가 미리 채워져 있기를 원한다. 그래야 일부만 고치기 쉽다.
27. 글쓴이로서, 올바른 글 비밀번호를 입력하면 메시지가 바뀌고 편집칸이 닫히기를 원한다.
28. 글쓴이로서, 수정해도 이름과 작성 시각은 그대로이기를 원한다. 이름은 수정할 수 없다.
29. 글쓴이로서, 수정에 성공하면 "(수정됨 · 수정 시각)"이 표시되기를 원한다.
30. 글쓴이로서, 글 비밀번호가 틀리면 수정이 거부되고 입력칸 아래에 "비밀번호가 일치하지 않습니다."가 표시되기를 원한다. 그래야 왜 안 됐는지 안다.
31. 글쓴이로서, 비밀번호가 틀려도 내가 고쳐 쓴 메시지가 지워지지 않기를 원한다. 그래야 비밀번호만 다시 입력하면 된다.
32. 글쓴이로서, 수정할 메시지가 비었거나 500자를 넘으면 거부되고 이유가 표시되기를 원한다.
33. 글쓴이로서, 편집 도중 "취소"를 누르면 편집칸이 닫히고 원래 메시지가 그대로 남기를 원한다.
34. 글쓴이로서, 수정하려는 글이 그사이 삭제되었다면 "이미 삭제된 글입니다."라는 안내를 받고 싶다.
35. 방문자로서, 다른 사람의 글에서 "수정"을 눌러도 올바른 글 비밀번호 없이는 아무것도 바꿀 수 없기를 원한다.

### 삭제

36. 글쓴이로서, 내 글의 "삭제" 버튼을 누르면 그 글 안에 글 비밀번호 입력칸이 펼쳐지기를 원한다.
37. 글쓴이로서, 올바른 글 비밀번호를 입력하면 글이 목록에서 사라지기를 원한다.
38. 글쓴이로서, 글 비밀번호가 틀리면 삭제가 거부되고 입력칸 아래에 "비밀번호가 일치하지 않습니다."가 표시되기를 원한다.
39. 글쓴이로서, 삭제하려는 글이 이미 삭제되었다면 "이미 삭제된 글입니다."라는 안내를 받고 싶다.
40. 글쓴이로서, 삭제 도중 "취소"를 누르면 입력칸이 닫히고 글이 그대로 남기를 원한다.
41. 방문자로서, 다른 사람의 글은 올바른 글 비밀번호 없이는 지울 수 없기를 원한다.

### 갱신

42. 방문자로서, 작성·수정·삭제에 성공하면 페이지 전체를 다시 불러오지 않고도 서버의 최신 목록으로 화면이 바뀌기를 원한다. 그래야 깜빡임 없이 스크롤 위치가 유지된다.
43. 방문자로서, 이때 다른 사람이 그사이 남긴 글도 함께 반영되기를 원한다.

## Implementation Decisions

### 용어

- 코드와 UI 문구는 용어집의 **글, 글쓴이, 메시지, 작성 시각, 수정 시각, 글 비밀번호**를 따른다.

### 방명록 모듈 (핵심 경계)

- 방명록 규칙은 화면과 Next.js에 의존하지 않는 서버 전용 모듈 하나에 모두 담는다. 이 모듈이 유일한 테스트 경계다.
- 모듈은 DB 연결(SQL 실행기)을 밖에서 주입받는다. 운영에서는 Neon 서버리스 드라이버, 테스트에서는 메모리 Postgres(PGlite)를 넣는다. 두 경우 모두 같은 SQL이 돌아야 한다.
- 공개 기능은 네 가지다.
  - **글 목록 조회**: 전체 글을 작성 시각 내림차순으로 반환한다. 반환하는 글에는 id, 이름, 메시지, 작성 시각, 수정 시각(없으면 비어 있음)만 있고, 글 비밀번호 해시와 salt는 절대 포함하지 않는다.
  - **글 작성**: 이름, 메시지, 글 비밀번호를 받는다.
  - **메시지 수정**: 글 id, 글 비밀번호, 새 메시지를 받는다. 성공하면 메시지와 수정 시각만 바뀐다.
  - **글 삭제**: 글 id, 글 비밀번호를 받는다. 성공하면 DB에서 완전히 지운다.
- 작성·수정·삭제는 예외를 던지는 대신 다음 중 하나의 결과를 돌려준다: `성공` / `입력값 오류(필드별 이유)` / `비밀번호 불일치` / `글 없음`. 화면은 이 결과를 그대로 안내 문구로 바꾼다.
- 결과 판정 순서: 입력값 검증 → 글 존재 여부 → 비밀번호 확인. 존재하지 않는 id는 `글 없음`이다.

### 입력값 규칙 (서버에서 강제)

- 이름: 앞뒤 공백 제거 후 1~20자.
- 메시지: 앞뒤 공백 제거 후 1~500자, 줄바꿈 허용.
- 글 비밀번호: 4~64자, 공백 제거하지 않음.
- 같은 제한을 브라우저 폼 속성에도 건다. 단, 신뢰의 기준은 서버 검증이다.

### 글 비밀번호

- Node 내장 scrypt로 해시하고, 글마다 무작위 salt를 쓴다. 비교는 타이밍 공격에 안전한 방식으로 한다.
- 평문 비밀번호는 저장하지도, 로그에 남기지도, 응답에 넣지도 않는다.
- 무차별 대입 제한(시도 횟수 제한)은 두지 않는다.
- 글 비밀번호를 잊으면 그 글은 수정·삭제할 수 없다. 관리자 경로는 없다.

### 스키마

- 테이블 하나: 글. 컬럼은 id(자동 증가), 이름, 메시지, 글 비밀번호 해시, salt, 작성 시각(`timestamptz`, 기본값 현재 시각), 수정 시각(`timestamptz`, 비어 있을 수 있음).
- 작성 시각 내림차순 조회를 위한 인덱스를 둔다.
- 스키마는 저장소의 SQL 파일로 관리하고, `npm run db:init` 스크립트로 `DATABASE_URL`이 가리키는 DB에 적용한다. 스크립트는 여러 번 실행해도 안전해야 한다.

### Next.js 연결 (얇은 어댑터)

- Next.js 16 App Router를 쓴다. 작업 전 저장소에 설치된 Next.js 문서(서버 함수, 데이터 변경 가이드)를 확인하고 그 규칙을 따른다.
- 페이지는 서버 컴포넌트에서 방명록 모듈의 목록 조회를 직접 호출해 렌더링한다. 항상 최신 데이터를 보여 줘야 하므로 정적으로 캐시하지 않는다.
- 작성·수정·삭제는 Server Action(서버 함수)으로 노출한다. 각 Action은 폼 데이터를 꺼내 방명록 모듈에 넘기고, 성공하면 페이지 데이터를 다시 불러오게(revalidate) 한 뒤 결과를 돌려준다. 규칙은 Action이 아니라 모듈에 둔다.
- 폼 상태(대기 중, 필드별 오류, 비밀번호 불일치, 글 없음)는 클라이언트 컴포넌트가 Action 결과로 표시한다.

### UI

- 한 페이지 구성: 제목 → `개발자: 이동규 (202404265)` → 작성 폼 → 글 목록.
- 각 글에 "수정", "삭제" 버튼이 있고, 누르면 그 글 안에서 입력칸이 펼쳐진다(모달이나 브라우저 prompt/alert는 쓰지 않는다). 한 글에서 수정과 삭제 입력칸이 동시에 열리지 않는다.
- 안내 문구: 비밀번호 불일치 → "비밀번호가 일치하지 않습니다.", 글 없음 → "이미 삭제된 글입니다.", 입력값 오류 → 필드별 이유.
- 시각 표시는 한국 시간(Asia/Seoul) `YYYY-MM-DD HH:mm`.
- 스타일은 Tailwind를 쓴다.

### 배포

- Vercel에 배포한다. 필요한 환경변수는 `DATABASE_URL` 하나다. 로컬에서는 `.env.local`에 둔다(이미 git에서 제외됨).

## Testing Decisions

- 좋은 테스트는 방명록 모듈의 **공개 기능을 통해 드러나는 동작**만 검증한다. 해시 형식, SQL 문장, 내부 함수 같은 구현 세부사항은 검증하지 않는다.
- 테스트 대상은 방명록 모듈 하나다. Vitest로 돌리고, DB로는 테스트마다 새로 만든 PGlite 인스턴스에 실제 스키마 SQL을 적용해 쓴다. 네트워크나 Neon은 필요 없다.
- 검증할 동작:
  - 작성한 글이 목록에 나타나고, 목록이 작성 시각 최신순이다.
  - 목록 결과에 비밀번호 관련 정보가 전혀 없다.
  - 이름·메시지 앞뒤 공백이 정리되어 저장된다.
  - 이름·메시지·글 비밀번호의 빈 값/길이 초과/길이 미달이 `입력값 오류`로 거부되고 아무것도 저장되지 않는다.
  - 올바른 글 비밀번호로 수정하면 메시지와 수정 시각만 바뀌고, 이름·작성 시각·목록 순서는 그대로다.
  - 틀린 글 비밀번호로 수정/삭제하면 `비밀번호 불일치`이고 글은 변하지 않는다.
  - 올바른 글 비밀번호로 삭제하면 목록에서 사라진다.
  - 없는 id(또는 이미 삭제된 글)에 대한 수정/삭제는 `글 없음`이다.
  - 글 비밀번호는 글마다 독립적이다: A 글의 비밀번호로 B 글을 수정/삭제할 수 없다.
- Server Action과 UI는 자동 테스트하지 않는다. Next 문서에 따르면 Vitest는 async Server Component를 지원하지 않으며, Action은 모듈을 부르는 얇은 어댑터다. 대신 개발 서버에서 작성·조회·수정·삭제와 각 오류 안내를 수동으로 확인한다.
- 저장소에 기존 테스트가 없으므로 참고할 선례는 없다. 이 작업에서 Vitest 설정과 `npm test` 스크립트를 새로 추가한다.

## Out of Scope

- 회원가입, 로그인, 계정.
- 이름 수정.
- 관리자 기능, 비밀번호 찾기/재설정.
- 비밀번호 시도 횟수 제한 등 무차별 대입 방어.
- 페이지 나누기, 무한 스크롤, 검색, 정렬 옵션.
- 다른 사람의 새 글이 실시간으로 뜨는 기능(작성·수정·삭제 후 갱신 시에만 반영).
- 삭제된 글 복구(소프트 삭제).
- 이미지, 링크 미리보기, 이모지 반응, 댓글.
- UI와 Server Action의 자동 테스트(E2E 포함).
